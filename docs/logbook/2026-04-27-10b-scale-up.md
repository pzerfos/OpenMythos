## Issues Encountered & Resolved

### 1. Multi-node blaunch failure (jobs 56133)

First attempt used 2 nodes × 8 GPUs = 16 GPUs. The bsub script used `blaunch` with env var
prefix syntax (`blaunch KEY=val bash -c "..."`). With `-n 2`, LSF allocated two nodes
(`p6-r06-n4`, `p4-r23-n3`) but blaunch failed with:

```
info:: line 5: p4-r23-n3: command not found
```

The job exited after 10 seconds. Root cause: `blaunch` with multiple allocated hosts and
env-var prefix syntax does not correctly distribute the command to the second node — the
second hostname ends up treated as a command token. Job ran for 10s and exited cleanly
(exit 0) without training.

**Fix:** Dropped to **single-node 8 GPUs**. Each BlueVela node has 8× H100 80GB.
`grad_accum` auto-adjusts to `max(1, 16 // (8×1)) = 2`, keeping global batch at
`8 × 1 × 2 × 2048 = 32,768` tokens/step — identical to the 4-GPU run. Step numbering
and LR schedule remain continuous.

### 2. ClearML artifact uploads blocking scalar reporting (job 56153)

After training started on 8 GPUs (job 56153), ClearML scalars stopped updating for ~10
minutes. Root cause: `register_clearml_artifact()` was uploading the full 18GB checkpoint
file to the ClearML file server on every `ckpt_every=1000` steps. This blocked ClearML's
background reporting thread, preventing scalar metrics from flushing. A second ClearML
task was also spuriously created (`c420fc0ca4324591b0904ebee2b81797`) due to the upload
stall/retry.

Additionally, 18GB checkpoints uploaded to ClearML's file server would quickly exhaust
its storage capacity.

**Fix:** Removed `register_clearml_artifact()` call from `save_checkpoint()`
(commit `20c753a`). Checkpoints are saved to the shared filesystem
(`/proj/checkpoints/pzerfos/openmythos/checkpoints`) — no need to duplicate them in
ClearML. ClearML now tracks scalars only.

Job 56153 was killed at step ~32,400 and resubmitted as job 56429 with the fix.
